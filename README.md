# ECG Denoiser FPGA Project

This repository is being developed from the PRD in [PRD-ECG-Denoising-Autoencoder-FPGA.md](PRD-ECG-Denoising-Autoencoder-FPGA.md).

Current milestone: Phase 1 — project structure and environment setup.

## Scope of Phase 1
- Establish a reproducible Python project structure.
- Define the package layout for future dataset, preprocessing, model, training, and FPGA export work.
- Provide a baseline configuration file and project smoke tests.
- Do not yet implement the ECG denoising pipeline itself.

## Repository layout
- `src/` — implementation code for each project stage.
- `scripts/` — runnable project entry points.
- `tests/` — project tests.
- `configs/` — YAML configuration files.
- `docs/` — design and specification notes.

## Status
This repository currently includes the project specification and the initial Phase 1 engineering scaffold only.

## Waveform visualizer
Run the local model-backed dashboard from the project root:

```bash
python scripts/visualizer.py
```

Open http://127.0.0.1:8000 in a browser. The dashboard loads deterministic windows from the test split, runs the checkpoint in `checkpoints/best_model.pt`, and shows the noisy input, denoised output, clean reference, residual noise, and per-window metrics. Use `--config`, `--checkpoint`, or `--port` to point it at another experiment.

Training progress can be written while an experiment runs:

```powershell
python scripts/train_model.py --epochs 60 --checkpoint checkpoints/model_60_epochs.pt --progress runs/model_60_epochs_progress.json
Get-Content runs/model_60_epochs_progress.json -Wait
```

The progress file is updated after every completed epoch with `completed_epochs`, `total_epochs`, the latest losses, and the best validation PRD.

## HLS export

HLS export requires an ONNX/hls4ml/QONNX toolchain in addition to the base
Python requirements. Install versions compatible with the installed Vitis
release, then export a trained checkpoint:

```powershell
python -m pip install onnx qonnx hls4ml
python scripts/export_hls.py `
  --checkpoint checkpoints/best_model.pt `
  --onnx artifacts/ecg_denoiser.onnx `
  --output-dir artifacts/ecg_denoiser_hls
```

The exporter uses a static `(1, 1, 256)` input, writes an ONNX intermediate,
strips Brevitas-only quantizer wrappers for the hls4ml PyTorch front end, and
generates a Vitis HLS project. Conversion errors are surfaced for missing
packages or unsupported operators; the generated project must still pass HLS
C simulation and synthesis before Vivado integration. The generated HLS graph
uses the trained convolution weights, but its fixed-point behavior must be
compared against the quantized PyTorch reference before hardware sign-off.

Create calibration directly from the configured WFDB records with:

```powershell
python scripts/create_config_calibration.py `
  --config configs/defaults.yaml `
  --output artifacts/input_calibration.json
```

## UART packet contract

The reference protocol is implemented in
[uart_protocol.py](C:/Users/varun/Documents/MyCode/ECGDenoiser.worktrees/fpga-model-deployment-zynq-zcu104/src/fpga/uart_protocol.py).
Each packet contains:

```text
magic       2 bytes: ASCII "EC"
version     1 byte: 1
flags       1 byte: 0
sequence    4 bytes: little-endian uint32
count       2 bytes: little-endian uint16, always 256
samples     512 bytes: 256 little-endian signed int16 samples
crc32       4 bytes: little-endian CRC32 over header and samples
```

The complete packet is 526 bytes. The configured 115200 baud link is
sufficient for one 256-sample packet at a time, but the receiver must validate
the sequence number and CRC before invoking inference.

## PYNQ runtime boundary

[runtime.py](C:/Users/varun/Documents/MyCode/ECGDenoiser.worktrees/fpga-model-deployment-zynq-zcu104/src/fpga/runtime.py)
contains the board-runtime boundary used after the Vivado overlay is built.
`process_window` expects an AXI DMA object with `sendchannel` and
`recvchannel`, and `process_uart_packet` connects that DMA operation to the
UART packet contract. On the board, allocate the input and output arrays with
`pynq.allocate` and pass the overlay's DMA object; the host-side tests use a
mock DMA object to verify sequencing and error handling.

The remaining board-specific work is to provide:

1. A `.bit`/`.hwh` overlay generated by Vivado.
2. A PYNQ notebook or service that opens the board UART.
3. A `read_exact` implementation that handles serial timeouts.
4. Deployment-specific cache synchronization if buffers are not coherent.

Once the overlay has been generated and copied to the board, start the PYNQ
service with:

```bash
python scripts/run_pynq_runtime.py \
  --bitstream /home/xilinx/jupyter_notebooks/ecg_denoiser/ecg_denoiser.bit \
  --serial-device /dev/ttyUSB1 \
  --dma-name axi_dma
```

The launcher imports `pynq` and `pyserial` lazily so the host development
environment does not need board-only packages. The DMA object name must match
the name exported by the Vivado overlay.

## Vivado block design

The initial ZCU104 block-design script is
[create_design.tcl](C:/Users/varun/Documents/MyCode/ECGDenoiser.worktrees/fpga-model-deployment-zynq-zcu104/hardware/vivado/create_design.tcl).
It targets the XCZU7EV device and connects the MPSoC, AXI SmartConnect, AXI
DMA, and packaged HLS accelerator. The HLS IP VLNV and stream interface names
must be confirmed after HLS packaging.

The complete hardware prerequisites and flow are documented in
[hardware/vivado/README.md](C:/Users/varun/Documents/MyCode/ECGDenoiser.worktrees/fpga-model-deployment-zynq-zcu104/hardware/vivado/README.md).

## Deployment preflight

Run this before attempting export or board bring-up:

```powershell
python scripts/check_fpga_prerequisites.py
```

It reports the checkpoint, ONNX, QONNX, hls4ml, PYNQ, and pyserial
requirements independently. A non-zero exit code means at least one
requirement is missing; it does not modify the environment.
