======================================================================
2. ARCHITECTURE DECISION
======================================================================

The original model was a spatial encoder/decoder:

    strided Conv1D -> bottleneck at 32 samples -> nearest UpSample1D -> output

That architecture was changed because the legacy hls4ml frontend available for
Vivado HLS 2019.1 did not support torch.nn.Upsample or the corresponding ONNX
Resize operation. Trying to force that architecture through the old frontend
was not productive.

The new deployment model is a fixed-length, same-length convolutional denoiser:

    Input: 1 x 256
    QuantConvBlock: 1  -> 16, kernel 7, stride 1, padding 3
    QuantConvBlock: 16 -> 32, kernel 5, stride 1, padding 2
    QuantConvBlock: 32 -> 32, kernel 3, stride 1, padding 1
    QuantConvBlock: 32 -> 16, kernel 3, stride 1, padding 1
    QuantConvBlock: 16 -> 8,  kernel 5, stride 1, padding 2
    QuantConv1D:      8  -> 1,  kernel 7, stride 1, padding 3
    Output: 1 x 256

Every layer preserves the 256-sample spatial length. The model uses only
operators that the legacy PyTorch frontend is expected to understand:
Conv1d, BatchNorm1d, and ReLU. The model must be retrained from scratch.
Existing checkpoints from the old encoder/decoder architecture are invalid.

The implementation is in:

    src/models/quant_autoencoder.py

The export wrapper was updated to use model.layers instead of model.encoder and
model.decoder.

4. ISSUES ENCOUNTERED DURING DEVELOPMENT
======================================================================

4.1 Original Vivado IP versions were unavailable

The first Tcl script requested zynq_ultra_ps_e:3.5 and proc_sys_reset:5.1.
Vivado 2019.1 returned no catalog entries for those exact versions. The
installed compatible versions are 3.3 and 5.0 respectively. This was fixed in
the Tcl script.

4.2 Vitis backend was wrong for Vivado 2019.1

The initial exporter used backend="Vitis". Vivado HLS 2019.1 predates the
Vitis HLS tool naming and flow. The exporter was changed to backend="Vivado".

4.3 Host prerequisites were initially missing

The global Python interpreter did not have pytest, torch, Brevitas, ONNX,
QONNX, hls4ml, PYNQ, or pyserial. A project virtual environment was configured
at:

    .venv/Scripts/python.exe

The base Python/model packages and export packages were installed there. PYNQ
is board-side software and is not expected to be installed on Windows.
Always use the project interpreter instead of the global Python interpreter:

    d:/blc1307/ECGDenoiser/.venv/Scripts/python.exe

4.4 No checkpoint was available

The prerequisite checker reported a missing checkpoint. A disposable random
weight checkpoint was used only for conversion smoke tests. It must never be
used as the deployment model. A real checkpoint must be produced by retraining
the new architecture on the ECG dataset.

4.5 No configured datasets were present

The configured noise directory and clean ECG directory are absent from this
workspace. The current config expects data locations under the repository,
including:

    mit-bih-noise-stress-test-database-1.0.0
    data/clean

The project input notes also reference a historical Windows path under
C:\Users\varun\Documents\MyCode\ECGDenoiser. That path is not present in the
current workspace and must be verified before training.

4.6 Original architecture contained unsupported Upsample layers

hls4ml 0.8.1 exposed support for Conv1d, BatchNorm1d, ReLU, pooling, reshape,
and similar operations, but not torch.nn.Upsample. Its ONNX frontend also did
not expose a usable Resize handler for this graph. This is why the architecture
was rewritten instead of retaining the original decoder.

4.7 hls4ml version/API differences

hls4ml 1.3.0 accepted the newer conversion call shape but generated a project
that Vivado HLS 2019.1 could not synthesize. hls4ml 0.8.1 has a different API:

- input shape must include the channel dimension
- batch dimension should be None
- config granularity uses layer rather than name
- Vivado fixed point uses ap_fixed<16,6>

The exporter was adapted for that API.

4.8 Vivado HLS 2019.1 compiler failure with hls4ml 1.3 output

A disposable full-graph hls4ml 1.3 project was generated successfully and
Vivado HLS 2019.1 began compiling it. C simulation passed after experimentation,
but RTL synthesis failed in Vivado HLS's bundled Clang 3.1/C++ 4.5.2 headers.
The errors included type_info and nested_exception failures, followed by
failure when the C++ standard flag was removed. This established that the
hls4ml 1.3 output/toolchain combination was not a reliable match.

Do not report HLS synthesis as successful based only on project generation or
C simulation. A real csynth result is required.

4.9 Legacy TensorFlow/Keras environment mismatch

After installing legacy hls4ml releases, imports encountered an environment
problem: qkeras expected tensorflow.keras, while the environment exposed a
split/mismatched TensorFlow and tf_keras installation. Observed package state
included TensorFlow 2.14.1 and tf_keras 2.21.0. This needs to be repaired or
isolated in a dedicated legacy export environment before hls4ml conversion can
be considered validated.

Do not silently work around this by changing the model or claiming the HLS
flow is proven. First make the package versions internally consistent.

4.10 PYNQ DMA buffer issue remains unresolved

src/fpga/runtime.py currently allocates ordinary NumPy arrays. Real PYNQ DMA
usually requires physically contiguous buffers allocated by pynq.allocate, and
cache synchronization may be needed depending on the platform. The runtime
abstraction tests use fake DMA and do not prove board operation.

4.11 UART exact-read issue remains unresolved

scripts/run_pynq_runtime.py passes serial port read directly into serve_uart.
Serial reads can return fewer bytes than requested. A read_exact function that
accumulates bytes until the 526-byte packet is complete, or raises on timeout,
must be implemented before board testing.

4.12 HLS IP interface names are not finalized

hardware/vivado/create_design.tcl assumes the packaged HLS IP exposes:

    s_axis
    m_axis
    s_axi_control
    ap_clk
    ap_rst_n

These names must be checked in the actual packaged IP. hls4ml may use different
port names or generate a wrapper interface. The Tcl block design must be
adapted to the actual VLNV and interface names after packaging.

4.13 Temporary/tool-generated files appeared during testing

Vivado and Vivado HLS generated temporary projects, logs, .Xil data, tb_data,
and crash/log files while testing. Review git status before committing. Do not
commit generated bitstreams, temporary HLS projects, crash dumps, or machine-
specific paths unless explicitly intended.

Step 7 - Run Vivado HLS 2019.1 validation

Use the installed Vivado HLS 2019.1 executable, not a Vitis executable. Run
C simulation first, then RTL synthesis. A successful result must include a
csynth report with no errors and resource/latency estimates.

If synthesis fails:

- Capture the complete vivado_hls.log.
- Identify whether the failure is generated C++, an unsupported operator, a
  compiler flag, an include/version conflict, or a resource issue.
- Do not modify the model solely to hide a compiler error without recording the
  reason.
- Keep the generated HLS project outside the source tree or clean it afterward.

Step 8 - Package the HLS IP

- Package the synthesized HLS output as Vivado IP.
- Record the exact VLNV.
- Inspect the AXI stream widths, TLAST behavior, AXI-Lite control ports, clock,
  and active-low reset.
- Confirm whether the stream transports one 256-sample window as 16-bit values.
- Confirm that DMA stream data width and HLS stream data width agree.

Step 9 - Build the ZCU104 block design

Use hardware/vivado/create_design.tcl with:

    set HLS_IP_VLNV "<actual packaged VLNV>"
    set PROJECT_NAME "ecg_denoiser_zcu104"
    set PROJECT_DIR "<absolute project directory>"
    source hardware/vivado/create_design.tcl

Then:

- Add the packaged IP repository before creating the HLS cell.
- Confirm the Zynq PS, DMA, SmartConnect, reset, and HLS IP cells exist.
- Resolve all address assignments.
- Run validate_bd_design.
- Confirm AXI DMA MM2S connects to HLS s_axis.
- Confirm HLS m_axis connects to AXI DMA S2MM.
- Confirm AXI-Lite control mapping.
- Confirm PS HP0/HP1 connections and clock/reset wiring.

Step 10 - Synthesize, implement, and generate the overlay

- Run Vivado synthesis.
- Review timing and utilization.
- Run implementation.
- Generate the bitstream.
- Generate/export the hardware handoff as needed by the PYNQ image.
- Copy the final .bit and .hwh to the board only after the reports are clean.

Step 11 - Fix the board runtime before bring-up

The current runtime needs board-specific completion:

- Replace ordinary NumPy DMA buffers with pynq.allocate buffers.
- Add cache flush/invalidate handling if required by the ZCU104/PYNQ image.
- Implement exact serial reads with timeout handling.
- Verify the overlay exposes the configured DMA name, currently axi_dma.
- Verify the UART device name on the ZCU104 image.
- Verify 115200 baud and the 526-byte packet contract.
- Confirm sequence and CRC handling under dropped/partial UART reads.

Step 12 - Hardware validation

Use deterministic golden vectors generated from the retrained checkpoint. Test:

- All-zero or constant input handling.
- Minimum and maximum int16 values.
- A normal ECG window.
- A noisy ECG window.
- Multiple consecutive packets.
- Packet sequence rollover behavior.
- CRC corruption rejection.
- DMA timeout/error handling.
- FPGA output against the quantized software reference within an agreed fixed-
  point tolerance.
