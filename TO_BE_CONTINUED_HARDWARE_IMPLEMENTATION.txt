======================================================================
2. ARCHITECTURE (UNCHANGED)
======================================================================

The deployment model is a fixed-length, same-length convolutional denoiser:

    Input: 1 x 256
    QuantConvBlock: 1  -> 16, kernel 7, stride 1, padding 3
    QuantConvBlock: 16 -> 32, kernel 5, stride 1, padding 2
    QuantConvBlock: 32 -> 32, kernel 3, stride 1, padding 1
    QuantConvBlock: 32 -> 16, kernel 3, stride 1, padding 1
    QuantConvBlock: 16 -> 8,  kernel 5, stride 1, padding 2
    QuantConv1D:      8  -> 1,  kernel 7, stride 1, padding 3
    Output: 1 x 256

Every layer preserves the 256-sample spatial length and uses only Conv1d,
BatchNorm1d, and ReLU, which hls4ml's PyTorch frontend supports under both
the legacy Vivado backend and the current Vitis backend. This architecture
choice remains correct for 2023.2 and does not need to change.

The implementation is in:

    src/models/quant_autoencoder.py

======================================================================
3. COMPATIBILITY CHANGES MADE FOR VIVADO/VITIS 2023.2
======================================================================

3.1 Vivado HLS was retired; the export backend must be Vitis

Xilinx stopped shipping Vivado HLS after the 2019.x release line. Vivado
2023.2 only installs Vitis HLS. The exporter (scripts/export_hls.py) was
changed from hls4ml backend="Vivado" to backend="Vitis" in both
config_from_pytorch_model and convert_from_pytorch_model. This is the single
most important change for 2023.2 compatibility: exporting with the old
"Vivado" backend string will not match the installed tool.

3.2 Vivado IP catalog versions are pinned to confirmed 2023.2 values

hardware/vivado/create_design.tcl previously pinned IP versions tuned for
Vivado 2019.1's catalog (zynq_ultra_ps_e:3.3, proc_sys_reset:5.0). These were
confirmed against a real Vivado 2023.2 install (via
`get_ipdefs -filter {VLNV =~ "xilinx.com:ip:<name>:*"}`) and are now pinned
directly:

    zynq_ultra_ps_e:3.5
    axi_dma:7.1
    smartconnect:1.0
    proc_sys_reset:5.0

(proc_sys_reset stayed at 5.0; the others moved up from the 2019.1 values.)
The script checks each pinned VLNV is present in the active IP catalog and,
only if it is missing (e.g. a later Vivado release drops that exact minor
version), falls back to resolving the highest available version for that IP
name via a resolve_ip_vlnv helper, with a printed warning. This keeps builds
reproducible against the verified 2023.2 versions while not hard-failing on
a future Vivado release that renumbers these IPs.

The custom HLS accelerator IP (HLS_IP_VLNV) is still supplied explicitly by
the caller, since it is produced by this project's own HLS packaging step,
not the standard catalog.

3.3 Tool executable paths

Update any saved paths/scripts referencing the old install to the 2023.2
install locations:

    Vivado 2023.2:    C:\Xilinx\Vivado\2023.2\bin\vivado.bat
    Vitis HLS 2023.2:  C:\Xilinx\Vitis_HLS\2023.2\bin\vitis_hls.bat

There is no vivado_hls.bat under a 2023.2 install; the equivalent commands
are exposed through vitis_hls.

3.4 hls4ml / Python export environment

The hls4ml==0.8.1 pin is retained (requirements.txt), since that release
already exposes a "Vitis" backend name -- only the backend argument passed by
scripts/export_hls.py needed to change, not the hls4ml version. This has not
been verified end-to-end against an installed Vitis HLS 2023.2 executable in
this workspace (no Vivado/Vitis install is present here); confirm hls4ml
actually invokes vitis_hls successfully as the first step of section 5.

3.5 Documentation

README.md, the PRD, and hardware/vivado/README.md were updated to describe
Vitis HLS 2023.2 and the Vitis hls4ml backend instead of Vivado HLS 2019.1.

======================================================================
4. THINGS THAT STILL NEED VERIFICATION ON A REAL 2023.2 INSTALL
======================================================================

These could not be confirmed without an installed Vivado/Vitis 2023.2
toolchain, since none is available in this workspace. Treat all of them as
open risks, not settled facts:

4.1 zynq_ultra_ps_e block-design properties

create_design.tcl sets PSU__USE__M_AXI_GP0, PSU__USE__S_AXI_GP2, and
PSU__FPGA_PL0_ENABLE on zynq_ultra_ps_e:3.5 (confirmed present in this
2023.2 install). These property names have been stable across many Vivado
releases, but they have not been confirmed against 3.5 specifically in this
workspace (no Vivado install here) -- run list_property on the cell after
creation to confirm before trusting the block design to build cleanly.

4.2 axi_dma interface widths

The AXI DMA CONFIG properties (c_m_axis_mm2s_tdata_width, etc.) are set
assuming the same DMA IP shape as before, now pinned to axi_dma:7.1
(confirmed present in this 2023.2 install). Confirm axi_dma:7.1 still exposes
identical CONFIG property names via list_property before trusting the
generated design.

4.3 hls4ml Vitis backend behavior differences

The Vitis backend in hls4ml is not a drop-in behavioral clone of the Vivado
backend -- default pragmas, interface synthesis (io_stream vs io_parallel
handling), and some resource/latency characteristics can differ. Do not
assume the HLS resource/latency numbers from any prior Vivado-backend run
carry over; re-run C simulation and synthesis with the Vitis backend and
record fresh numbers.

4.4 hls4ml/TensorFlow/QKeras environment consistency

If QKeras/TensorFlow-based export paths are used alongside hls4ml, verify the
installed TensorFlow/tf_keras/QKeras versions are mutually consistent in the
export environment, independent of the Vivado/Vitis version. This was an
open issue in the 2019.1 pass and is unrelated to the toolchain bump; it must
still be checked.

4.5 Everything in section 4 of the prior notes about PYNQ DMA buffers, UART
exact-read handling, and finalized HLS IP interface names remains open and is
not affected by the toolchain version change. See section 6 below for the
carried-over work items.

Step 2 - Restore the datasets

- Put the clean ECG records in the path configured by configs/defaults.yaml.
- Put the nstdb em and bw records in the configured noise directory.
- Ensure each WFDB record has the required .hea and .dat files.
- Run the dataset validation tests.
- Do not begin expensive training until the dataset checks pass.

Useful checks:

    python -m pytest -q tests/test_dataset_assembly.py tests/test_dataset_validation.py tests/test_wfdb_acquisition.py tests/test_torch_dataset.py

Step 3 - Recreate calibration (only if not already produced)

    python scripts/create_config_calibration.py `
      --config configs/defaults.yaml `
      --output artifacts/input_calibration.json

Step 4 - Train or reuse an existing checkpoint

If a valid checkpoint for the current architecture (src/models/quant_autoencoder.py)
already exists, reuse it; this toolchain update did not change the model. If
none exists yet:

    python scripts/train_model.py `
      --config configs/defaults.yaml `
      --checkpoint checkpoints/best_model.pt `
      --progress runs/retrained_progress.json

Step 5 - Evaluate the model

Run the project evaluation commands/tests and confirm MSE, output SNR, SNR
improvement, PRD, and morphology checks meet the PRD targets.

Step 6 - Export ONNX and HLS with the Vitis backend

    python scripts/export_hls.py `
      --checkpoint checkpoints/best_model.pt `
      --onnx artifacts/ecg_denoiser.onnx `
      --output-dir artifacts/ecg_denoiser_hls

Check that:

- The exporter loads the checkpoint.
- ONNX is generated.
- The HLS project is generated with backend="Vitis".
- The generated project targets xczu7ev-ffvc1156-2-e, not the default xcvu13p.
- The generated HLS precision matches the intended fixed-point contract.
- The generated top-level interfaces are recorded before packaging.

Note: the four standard block-design IP versions (zynq_ultra_ps_e:3.5,
axi_dma:7.1, smartconnect:1.0, proc_sys_reset:5.0) are already confirmed
present in this Vivado 2023.2 install and pinned in create_design.tcl; no
further catalog check is needed for those before Step 9.

Step 7 - Run Vitis HLS 2023.2 validation

Use the installed Vitis HLS 2023.2 executable. Run C simulation first, then
RTL synthesis. A successful result must include a csynth report with no
errors and resource/latency estimates.

If synthesis fails:

- Capture the complete vitis_hls.log.
- Identify whether the failure is generated C++, an unsupported operator, a
  compiler flag, an include/version conflict, or a resource issue.
- Do not modify the model solely to hide a compiler error without recording
  the reason.
- Keep the generated HLS project outside the source tree or clean it
  afterward.

Step 8 - Package the HLS IP

- Package the synthesized HLS output as Vivado IP.
- Record the exact VLNV.
- Inspect the AXI stream widths, TLAST behavior, AXI-Lite control ports,
  clock, and active-low reset.
- Confirm whether the stream transports one 256-sample window as 16-bit
  values.
- Confirm that DMA stream data width and HLS stream data width agree.

Step 9 - Build the ZCU104 block design

Use hardware/vivado/create_design.tcl with:

    set HLS_IP_VLNV "<actual packaged VLNV>"
    set PROJECT_NAME "ecg_denoiser_zcu104"
    set PROJECT_DIR "<absolute project directory>"
    source hardware/vivado/create_design.tcl

The script now auto-resolves standard Xilinx IP versions from the installed
2023.2 IP catalog (see section 3.2); only HLS_IP_VLNV needs to be supplied.

Then:

- Add the packaged IP repository before creating the HLS cell.
- Confirm the Zynq PS, DMA, SmartConnect, reset, and HLS IP cells exist.
- Resolve all address assignments.
- Run validate_bd_design.
- Confirm AXI DMA MM2S connects to HLS s_axis.
- Confirm HLS m_axis connects to AXI DMA S2MM.
- Confirm AXI-Lite control mapping.
- Confirm PS HP0/HP1 connections and clock/reset wiring.

Step 10 - Synthesize, implement, and generate the overlay

- Run Vivado synthesis.
- Review timing and utilization.
- Run implementation.
- Generate the bitstream.
- Generate/export the hardware handoff as needed by the PYNQ image.
- Copy the final .bit and .hwh to the board only after the reports are clean.

Step 11 - Fix the board runtime before bring-up

The current runtime needs board-specific completion:

- Replace ordinary NumPy DMA buffers with pynq.allocate buffers.
- Add cache flush/invalidate handling if required by the ZCU104/PYNQ image.
- Implement exact serial reads with timeout handling.
- Verify the overlay exposes the configured DMA name, currently axi_dma.
- Verify the UART device name on the ZCU104 image.
- Verify 115200 baud and the 526-byte packet contract.
- Confirm sequence and CRC handling under dropped/partial UART reads.

Step 12 - Hardware validation

Use deterministic golden vectors generated from the checkpoint. Test:

- All-zero or constant input handling.
- Minimum and maximum int16 values.
- A normal ECG window.
- A noisy ECG window.
- Multiple consecutive packets.
- Packet sequence rollover behavior.
- CRC corruption rejection.
- DMA timeout/error handling.
- FPGA output against the quantized software reference within an agreed
  fixed-point tolerance.
